# Migrating an existing project

The target: each citing note carries its own `references:` frontmatter block with full metadata; the bib is auto-generated by `cite-tool`.

Two starting points are common.

## From a hand-edited `references.bib` + body `[@key]` cites

For each cited bib entry:

1. Find the notes that cite it (`grep -rl "@<key>" .
  `).
2. For each such note, copy the bib entry's metadata into the note's frontmatter `references:` array:
   ```yaml
   references:
     - key: <key>
       type: article  # match the bib type
       authors: [...]
       year: ...
       title: "..."
       journal: "..."
       # ... etc.
   ```
3. Repeat for the next bib entry.
  If a paper is cited by 50 notes, the metadata gets duplicated 50 times — `cite-tool` will surface any `inline-mismatch` warnings if the duplicates drift.
4. Once every body cite is covered by a note's frontmatter, run `cite-tool generate` and confirm the regenerated bib matches your hand-edited one (or is close enough — non-standard fields and ordering may differ).
5. Delete the hand-edited `references.bib`.
  The composer regenerates it on each build.

## From a `references/` directory with no inline manifests yet

Easier — the metadata's already collected, just needs to move where it belongs.

1. For each note that cites a source kept in `references/<key>.md`, add an inline `references:` entry with the full metadata.
  Use the contents of that annotation file's frontmatter as the starting point.
2. Add `[@key]` body citations at the points the source is invoked.
3. Run `cite-tool generate` and confirm the bib is correct.
4. Run `program-validator` and confirm `cite-not-in-manifest` and `manifest-key-unresolved` are clean.
5. The `references/` directory can stay (as a place for prose research notes about each source), or be deleted entirely — your call.
  Either way the bib is correct.

## Cite-key renames

If your existing keys don't follow Better BibTeX form, you can keep them as-is or rename.
Renames need to be done atomically:

1. Pick the new key (`arnold1995remarks`).
2. Update every body cite: `[@arnold-1995-old-form]` → `[@arnold1995remarks]`.
3. Update every inline manifest entry's `key` field.
4. If you have a `references/<old-key>.md`, rename it.
5. Run `cite-tool check` to confirm nothing's dangling.

For bulk renames a small sed script over the corpus is usually enough once you've enumerated the rename pairs.

## What the validator catches mid-migration

Two rules are relevant:

- `cite-not-in-manifest` — body cites a key that's not in the note's `references:`.
  Either add it to the manifest or remove the body cite.
- `manifest-key-unresolved` — the note's manifest declares a key with no metadata anywhere in the project.
  Fill out the inline metadata.

A clean migration ends with both at zero.
