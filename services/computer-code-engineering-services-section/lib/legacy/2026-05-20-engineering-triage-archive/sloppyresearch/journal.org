I've written about it in a few places that are probably scattered, but I hit a complexity wall with my research that led to me basically freezing, at least when it comes to taking notes about it, and that's unfortunate because it coincides with when there are a couple folk near me who are more curious about what I'm working on.

Unfortunately, at this exact moment, I'm forgetting the vocabular I've been using to describe the shape of things in my head, and how that applies to doing my research. Not in the broad sense of like, doing research, but specifically in the sense of, producing text and computer code that result in stabilizing the research itself, and being able to communicate it better to other folk.

Part of that has involved just turning over the concept in a bunch of different ways, that I regret not having better journals on. But one thing that comes up often is that, in the interest of making things compatible with each other, through the "relational modality" I'm developing, is reducing them to "cells" that have "edges," and these edges can be used to form a categorical or geometric sense of how stuff fits together.

Providing those edges is a large part of what Org-mode and Org-roam do, if we think about things in that way, and that got me toward about how there are already quite a few edges encoded in files, by virtue of them living on a system and, in my case, usually in a Git repository.

For example, files have paths, filenames, and extensions, which give them a MIME type. They have a size, and a hash. They have timestamps: creation, modification, access. They have other things like filesystem permissions.

And Git gives us commit hashes, tree hashes, branches, tags, stages, commit counts, renames, authors, more timestamps, and commit messages. (I think I could probably be using Git commit messages a lot better than I am.)

There's more, and that's before even getting into what any file might specify in itself, i.e. TOML frontmatter in Markdown files. That stuff varies a lot by file format, so would need various ingesters to deal with - which, saying "ingester," there makes me think of this as kind of a semiotic organ we can install to a Git repository, "Repo as Relational Topology," less metaphorically though.

The base unit, our relational cell, =RelCell=, would be a =(branch, commit, path)=, and have a set of edges, =(Predicate TargetCell Provenance)=, that would be populated through our topology generator, i.e. the MIME type guesser runs on =foo.md@aabbccd= and gets us =(media_type text/markdown (:claimed-by "filesystem.mimetype_inferrer"))= or similar.

At runtime - probably hooked into Git hooks or something like GitHub Actions, an ingestor walks the repository, and for each branch, iterates files at HEAD. Registered ingestors are applied, and the RelCells are popualted into some sort of graph, probably saved as SQLite and/or JSON-LD.

My idea is that, that graph can then be used to create branches that have *just* the files we want to work on, does whatever is appropriate with them, and then... whatever. This might be, sets them aside for me to look at, edit, and merge back in. Or it might be to take them and publish them as a single PDF and mark that as the release file for that branch.

Part of the design here is that this is something could work with varying fitness on any Github repository, which lets me continue moving toward compatibility with the open sciences. It also lets me move toward standard tools that are compatible with the increasingly automated Web, and I could see being able to produce things like an RDF vocabulary from my own research by doing Spacy language processing on it as a way to let ingestors increase their ability to parse specific repositories.

Another angle is that presently, to work with my research requires a buy-in to the Emacs and Org-mode ecosystem that isn't really necessary. I wanted to press myself on how unnecessary by considering what it would look like to use the three tools that have become near-standard across a lot of the Web: Git, Python, and Markdown.

Which brings me to the meta question of how I should encode this journal entry, so that I can point to it as, "This is the origin of why I'm writing this little Python library," that I'll begin working on now that I've laid this out. My guess is within a Git commit message, and there is probably a standard way of referencing earlier commits within commit messages - nuances of Github-Flavored Markdown, I'm sure; which points to another reason why I'm leaning toward this way of doing things: it forces me to get more familiar with the systems I'm already using, kind of forcing me to reflect on my own "illusion of explanatory depth," which is a reference to recent personal conversations I've been having about where people fail to provide cognitive care toward stuff, that while a part of the research, isn't a part of this plan - but does bring up /yet another question/ of where do questions such as these go? Do we use Github Issues? Are those localized into the repository? I don't know, and I'm realizing that I've actually stumbled into a rather large open-question: where does futurity live, in this system. I've accounted for making future, through the projection of queries into branches, but not the making of futurity: an imaginary of the future: plans, questions, problems, potential solutions, etc.

Files give us space, Git gives us past-time, our interfaces of choice handle the present.

We don't necessarily *need* futurity, in the way I'm thinking, except that it is just a good convenenice for allocating human labor, at least until such things as play become more emergent from the system - and even then, I imagine, futurity might eb the play-space of such a game.

But, the immediate question is how to encode *this* act of presence, this journal entry... though maybe answering both at the same time is best.
